MASTER REQUIREMENTS — SCALABLE SOFTWARE REVIEW WEBSITE
Version: 2.0
Status: Based on the completed Fuxi Medianet implementation
Purpose: Reuse this specification to launch multiple independent software-review websites from the same proven architecture.

======================================================================
1. ROLE AND DELIVERY OBJECTIVE
======================================================================

Act as a senior React/TypeScript engineer, SEO architect, UX designer, structured-data specialist, and static-site publishing engineer.

Build a production-ready software review website that:

- Publishes hundreds or thousands of product reviews from structured JSON.
- Keeps archive pages lightweight by loading a manifest rather than every complete review.
- Gives every published review a unique, canonical, prerendered HTML page.
- Produces valid metadata, JSON-LD, sitemap.xml, and robots.txt.
- Works as a fully static deployment with no database or runtime backend.
- Supports automated research generation while allowing manual editorial edits.
- Can be cloned for a new brand without rewriting the application architecture.

The result must feel like an independent software research publication, not a thin affiliate directory or generic AI blog.

4. PROJECT STRUCTURE AND RESPONSIBILITIES
======================================================================

Preserve this separation of concerns:

public/data/partnerdata.json
- Raw PartnerStack/product source data.
- Large source file; never import it directly into the client JavaScript bundle.

public/data/reviews/index.json
- Lightweight review manifest used by homepage, review archive, product archive, prerender, and sitemap generation.
- Contains summary fields only.

public/data/reviews/<slug>-review.json
- One complete generated review per file.
- Manually editable after generation.
- Source of truth for generated review detail pages.

.cache/partner-review-research/
- Temporary Serper/research cache.
- Must be ignored by Git through .cache/ in .gitignore.
- Never deploy or commit API research cache unless explicitly required.

script_create_review/generate-partner-reviews.mjs
- Reads product source data.
- Researches products.
- Generates individual review files.
- Updates the manifest.
- Supports cached retries and publishing workflow.

src/types/content.ts
- Canonical TypeScript contracts for frontend review data and generated review data.

src/data/generatedReviews.ts
- Loads generated JSON in the browser.
- Validates publish state and schema version.
- Normalizes generated review data into the frontend ReviewProject model.
- Exports the normalizer for build-time prerendering.

src/pages/HomePage.tsx
- Manifest-driven homepage summary list.

src/pages/ArchivePages.tsx
- Manifest-driven complete review archive and PartnerStack product directory.

src/pages/ReviewPage.tsx
- Full review detail renderer and JSON-LD producer.
- Generated review JSON takes precedence over duplicate static review content.

src/components/seo/SEO.tsx
- Canonical metadata, robots, Open Graph, Twitter, and JSON-LD output.

scripts/prerender.tsx
- Build-time HTML rendering.
- Reads the generated review manifest and detail JSON.
- Produces one HTML file per public route.
- Produces sitemap.xml, robots.txt, feed.xml, and route-manifest.json.

src/styles/
- Keep page-level styles modular.
- Do not place all styles in one growing file.

5. DATA ARCHITECTURE
======================================================================

5.1 Review manifest contract

public/data/reviews/index.json must contain:

{
  "schemaVersion": 1,
  "generatedAt": "ISO-8601 timestamp",
  "reviews": [
    {
      "slug": "product-review",
      "name": "Product Name",
      "category": "Category",
      "status": "published",
      "score": 8.6,
      "excerpt": "Concise review summary.",
      "updatedAt": "YYYY-MM-DD",
      "cover": {
        "src": "https://...",
        "alt": "Descriptive image alt text",
        "caption": "Optional source caption"
      },
      "file": "product-review.json"
    }
  ]
}

Manifest requirements:

- slug must be unique.
- status must support draft and published.
- Only published records appear publicly.
- score uses the generated 10-point scale.
- file must point to an existing JSON file.
- excerpt must be useful as a card summary and meta-description fallback.
- updatedAt must be a valid date.
- The manifest must not contain full article sections or large research payloads.

5.2 Full generated review contract

Each review must use schemaVersion 2 and include:

- id
- slug
- status
- name
- entityType
- category
- tagline
- summary
- website
- brand
- partner/source identity
- publishedAt
- updatedAt
- evidence level
- methodology metadata
- media
- author
- highlights
- offer
- primary and secondary keywords
- rating value, scale, label, and weighted criteria
- verdict
- pros
- cons
- bestFor
- notIdealFor
- key facts
- content sections
- FAQ
- images
- sources
- generation metadata

5.3 Media contract

Use:

media: {
  cover: {
    src: string,
    alt: string,
    caption?: string
  },
  gallery: Array<{
    src: string,
    alt: string,
    caption?: string
  }>,
  youtubeUrl?: string,
  videoUrl?: string,
  videoTitle: string
}

Rules:

- youtubeUrl is preferred for official YouTube watch, share, Shorts, live, or embed links.
- videoUrl remains available for Vimeo or direct video files.
- Do not render any video UI when both URLs are empty.
- Cover images must use descriptive alt text.
- Manual media edits in generated JSON must appear immediately and must not be overridden by static fallback data.

5.4 Rating contract

- Generated JSON uses a 10-point scale.
- Frontend normalization may display a 5-point scale where required by the existing detail UI.
- Criteria must include key, label, score, weight, and summary.
- Criteria weights should total 100.
- Scores must be evidence-conscious and must not imply hands-on testing unless actual testing occurred.

6. CONTENT GENERATION WORKFLOW
======================================================================

The generator must:

1. Read eligible products from public/data/partnerdata.json.
2. Exclude unapproved, archived, test, or invalid products.
3. Resolve the official website URL.
4. Use Serper search/scrape evidence where enabled.
5. Cache research responses under .cache/partner-review-research/.
6. Generate one review JSON per product.
7. Write or update public/data/reviews/index.json.
8. Support draft and published output.
9. Use atomic writes for shared files such as index.json.
10. Retry transient API or filesystem failures.
11. Support cached-only retries so failed manifest writes do not consume new API credits.
12. Never erase manual youtubeUrl, videoUrl, or cover edits during unrelated regeneration unless overwrite is explicitly requested.

Recommended commands:

Generate/publish all eligible products:

npm run reviews:partners -- --publish

Generate selected IDs:

npm run reviews:partners -- --ids 10350,9186 --limit 2 --publish

Retry from cache:

npm run reviews:partners -- --ids 10350,9186 --limit 2 --cached-only --publish

Security requirement:

- Prefer environment variables or a secret manager for API keys on new websites.
- Never expose a Serper/API key in browser JavaScript, public JSON, static HTML, logs, or Git history.
- If a direct script constant is required by a private local workflow, keep the script server-side/build-time only and exclude real credentials from distributed templates.

Editorial requirements:

- Separate verified facts, vendor claims, and editorial conclusions.
- Cite source URLs in generated data.
- Do not invent pricing, customer counts, integrations, certifications, or hands-on experience.
- Avoid repetitive filler and unsupported superlatives.
- Keep visible copy useful even without affiliate links.
- Research/methodology metadata may remain in JSON without being displayed as a repetitive UI block.

16. PRERENDERING AND STATIC SEO OUTPUT
======================================================================

A pure SPA is not acceptable for SEO-critical routes.

scripts/prerender.tsx must:

1. Read dist/index.html after the Vite build.
2. Build a complete route list.
3. Read public/data/reviews/index.json.
4. Filter published reviews.
5. Load every published review detail JSON.
6. Normalize each generated review.
7. Inject the matching review into App during server rendering.
8. Render complete review HTML—not a loading shell.
9. Collect Helmet title, meta, link, script, and HTML attributes.
10. Write dist/<route>/index.html.
11. Generate sitemap.xml.
12. Generate robots.txt.
13. Generate feed.xml.
14. Generate route-manifest.json.

Required route coverage:

- All static public pages.
- All generated published review routes.
- All retained static product/article/comparison/category/author routes.
- /disclaimer/.

Review hydration contract:

- App accepts an optional initialReview.
- ReviewPage uses initialReview only when its slug matches the current route.
- Browser navigation still fetches generated review JSON normally.
- Prerendered HTML contains the full article and JSON-LD.

17. SITEMAP.XML REQUIREMENTS
======================================================================

Generate dist/sitemap.xml during every production build.

Include:

- Homepage.
- Products archive.
- Reviews archive.
- Every published generated review.
- About.
- Contact.
- Disclaimer.
- Editorial policy.
- Affiliate disclosure.
- Privacy policy.
- Terms.
- Other retained indexable content routes.

Exclude:

- /404/.
- /search/.
- Draft reviews.
- Missing review files.
- Internal cache/data URLs.

Each review URL should include lastmod from updatedAt.

All loc values must:

- Be absolute.
- Use the production SITE.url.
- Use trailing slashes consistently.
- Be XML escaped.

For future sites exceeding 50,000 URLs or 50 MB uncompressed, generate a sitemap index and split child sitemaps by content type or chunk.

======================================================================

======================================================================
24. CONTENT QUALITY ACCEPTANCE
======================================================================

Reject or revise content that:

- Claims hands-on testing without evidence.
- Invents prices, features, integrations, security claims, customers, or awards.
- Repeats the same generic paragraph across many reviews.
- Uses unsupported “best,” “number one,” or guarantee language.
- Hides important limitations.
- Uses an affiliate CTA as the main substance of the page.
- Has no clear best-for or not-for guidance.
- Has FAQ answers unrelated to visible content.
- Uses broken or irrelevant cover images.
- Uses undated or unverifiable claims as current facts.

Every published review should help a reader understand:

- What the product is.
- Who it is for.
- What it does well.
- What limitations to consider.
- How the score was formed.
- What should be verified before purchase.
- Where to find the official product source.

The website is complete only when:

1. Homepage displays concise generated review summaries.
2. Review archive exposes every published review.
3. Product directory links to available reviews.
4. Every review detail route loads generated JSON correctly.
5. Manual cover and video edits appear on the page.
6. About, Contact, and Disclaimer are complete and readable.
7. Metadata and social tags are present.
8. Review JSON-LD is present and aligned with visible content.
9. Every published review has full prerendered HTML.
10. sitemap.xml contains every indexable published route.
11. robots.txt references sitemap.xml.
12. TypeScript and production build pass.
13. Cache and secrets are excluded from Git.
14. The site can be deployed as static files from dist/.
15. A new brand can be launched by replacing configuration, assets, legal/contact details, and data—without rewriting the core review architecture.
